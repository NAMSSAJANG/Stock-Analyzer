## 2. 제품 원칙

모든 설계 판단은 "이 숫자를 믿어도 되는가"를 먼저 묻습니다. 아래 일곱 가지는 모든 Phase에 적용됩니다.

1. **점수는 메타데이터와 함께 다닌다.** 모든 점수 객체는 `value`, `percentile`, `coverage`(0~1), `as_of`(데이터 시점), `sources`, `evidence`(검증 상태)를 가진다.
2. **결측은 결측으로 표시한다.** 0이나 50으로 메우지 않는다. 핵심 요소가 빠지면 헤드라인 점수 옆에 '부분 점수 · 재무 제외' 같은 배지를 붙인다.
3. **점수는 정수로 표시한다.** 소수점은 실제보다 정밀해 보이게 만든다. 내부 계산은 실수로 한다.
4. **미래 정보를 쓰지 않는다.** 백테스트는 그 날짜에 실제로 알 수 있었던 데이터(point-in-time)만 쓴다. 현재 재무 스냅샷을 과거 날짜에 쓰지 않는다.
5. **파라미터는 미리 정하고 검증한다.** 조정이 필요하면 학습 구간에서만 하고, 검증 구간 결과로 확인한다. 시도한 변형의 수를 기록한다.
6. **투자 조언처럼 말하지 않는다.** '매수' 대신 '조건 충족', '확률' 대신 '과거 유사 구간의 성과'라고 쓴다. 모든 화면 하단에 "정보 제공·학습 목적이며 투자 조언이 아닙니다" 문구를 둔다.
7. **브랜드는 교체 가능한 테마로 분리한다.** 지금은 개인용 테마를 쓴다. 공개 배포 전에는 테마와 로고를 자체 브랜드로 바꾸고, 하단에 "Goldnam Sachs는 개인 프로젝트이며 Goldman Sachs와 관련이 없습니다"를 넣는다.

## 3. 아키텍처

계산은 웹과 분리된 순수 파이썬 엔진이 맡고, 무거운 유니버스 계산은 배치가 미리 해 둡니다. API와 웹은 그 결과를 읽기만 합니다.

```text
[외부 데이터]        [goldnam_engine]       [배치 작업]            [Render Postgres]
yfinance · FDR  ──▶  팩터·점수·타이밍  ──▶  GitHub Actions    ──▶  점수·검증 요약
SEC · OpenDART       리스크·검증            또는 Render Cron        관심종목·기록
                          ▲                                           │ 결과 읽기
                          ┆ (유니버스 밖 종목은 즉석 계산)              ▼
                          └┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄┄  [API]
                                                                    FastAPI
                     [NAMSSA]       ◀──      [웹]              ◀──  Render Web Service
                     브라우저·모바일          Next.js 정적 빌드
                                             Render Static Site
```

배치가 엔진으로 점수와 검증을 계산해 Postgres에 적고, API와 웹은 그 결과를 읽습니다. 그래서 API가 잠들었다 깨어나도 다시 계산할 게 거의 없습니다.

| 구성 요소 | 기술 | 역할 |
| --- | --- | --- |
| `engine` (패키지 `goldnam_engine`) | Python 3.12, pandas, numpy | 데이터 어댑터, 팩터, 점수, 타이밍, 리스크, 검증, 매매 계산. 웹 의존성 없음 |
| `jobs` | Python CLI | 매일 장 마감 후 유니버스 점수 계산, 주 1회 검증 실행 |
| 저장소 | Render Postgres, 로컬 Parquet 캐시 | 점수·검증 결과·관심종목·기록·설정은 Postgres(영구). 원시 시세 캐시는 Parquet(지워져도 다시 받음) |
| `api` | FastAPI, Pydantic | 엔진과 저장소를 감싼 REST API, OpenAPI 스키마 제공 |
| `web` | Next.js(App Router), TypeScript, Tailwind | 화면. API 타입은 OpenAPI에서 자동 생성 |
| 차트 | lightweight-charts(가격), ECharts 또는 Recharts(나머지) | 캔들·Zone·계획선, 팩터 막대, 검증 차트 |

**데이터 흐름.** 외부 소스 → 어댑터 → 로컬 저장소 → 배치(유니버스 점수, 검증 결과) → API → 웹 순서입니다. 사용자가 유니버스 밖 종목을 검색하면, API가 그 종목만 즉석 계산하고 같은 날의 유니버스 분포에 대입해 백분위를 매깁니다.

**배포: Render.** 개인용으로 Render에 올립니다. 로컬 개발은 `docker compose up` 한 번으로 같은 구성이 뜨게 합니다. Render 설정은 저장소의 `render.yaml`(Blueprint)로 코드화합니다.

| 구성 요소 | Render 서비스 | 이유 |
| --- | --- | --- |
| `web` | Static Site (Next.js 정적 내보내기) | 무료이고 잠들지 않음. 모든 데이터는 API에서 받으므로 서버 렌더링이 필요 없음 |
| `api` | Web Service (Python) | Free는 15분 미사용 시 잠들고 깨어나는 데 약 1분 걸림. 불편하면 Starter로 올림 |
| 저장소 | Render Postgres | 무료 웹 서비스는 파일시스템이 임시라 재시작하면 SQLite·파일이 사라짐 |
| 일일 점수 계산 | Render Cron Job 또는 GitHub Actions | Cron Job은 실행 시간만큼 과금(월 최소 $1). 비용을 피하려면 GitHub Actions가 계산해 Postgres에 기록 |
| 검증(무거움) | 로컬 또는 GitHub Actions | 10년·수백 종목 재계산은 웹 서비스에서 돌리지 않음. 요약 결과만 Postgres에 업로드 |

설계 규칙은 세 가지입니다. API는 상태를 로컬 디스크에 두지 않습니다. 잠들었다 깨어나도 첫 응답이 깨지지 않게, 웹은 '서버 준비 중' 화면을 보여주고 재시도합니다. 모든 비밀값(DB URL, OpenDART 키, SEC 연락처)은 Render 환경변수로만 넣습니다.

Render 무료 플랜의 세부 한도(무료 Postgres 용량과 만료 기간 등)는 바뀜 수 있습니다. GPT는 [Render 무료 플랜 문서](https://render.com/docs/free)와 [요금표](https://render.com/pricing)를 확인해 점수·시세 테이블 크기를 그 안에 맞추고, 넘치면 보관 기간을 줄이는 정책을 제안합니다.

## 4. 데이터 계층

모든 데이터는 공급자 어댑터를 거치고, 어떤 소스에서 언제 가져왔는지 기록을 남깁니다. 소스 하나가 막혀도 앱은 다음 소스로 넘어가거나, 비어 있다고 정직하게 표시합니다.

### 인터페이스

`PriceProvider`, `FundamentalsProvider`, `CalendarProvider`, `FxProvider`, `UniverseProvider` 다섯 개를 추상 클래스로 둡니다. 각 호출은 `DataResult(data, source, fetched_at, as_of, status, message)`를 반환합니다. `status`는 `ok`, `partial`, `stale`, `failed` 중 하나입니다.

### 소스 우선순위

| 데이터 | 미국 1순위 | 한국 1순위 | 폴백 |
| --- | --- | --- | --- |
| 일봉 OHLCV(수정주가) | yfinance | FinanceDataReader | 상대 시장의 1순위 소스 |
| 지수·ETF·VIX·금리 | yfinance | FinanceDataReader(KS11, KQ11) | yfinance |
| 재무(백테스트용, PIT) | SEC EDGAR XBRL companyfacts, 공시일(`filed`) 기준 | OpenDART 재무제표 API, 접수일 기준 | 없음. 해당 기간은 재무 팩터를 백테스트에서 제외 |
| 재무(현재 화면용) | PIT 저장소의 최신값 | PIT 저장소의 최신값 | yfinance `info` |
| 실적 발표일 | yfinance calendar | 확보 가능한 소스 조사 후 결정 | 없으면 '미확인' |
| 환율(USD/KRW) | yfinance `KRW=X` | FinanceDataReader | 마지막 성공값 + stale 표시 |
| 유니버스 구성 | S&P 500 ∪ Nasdaq-100 | KOSPI 200 ∪ KOSDAQ 150 | 저장된 마지막 구성 |

SEC는 요청 헤더에 연락처가 담긴 User-Agent를 요구하고 초당 요청 한도가 있습니다. OpenDART는 API 키가 필요합니다. 둘 다 GPT가 공식 문서에서 현재 규칙을 확인하고, 키와 연락처는 `.env`에서 읽습니다.

### 캐시 정책

- 성공한 시세는 다음 장 마감까지, 재무는 24시간 보관합니다.
- 실패는 성공으로 캐시하지 않습니다. 같은 요청의 반복 실패를 막는 음성 캐시는 5분까지만 둡니다.
- 재시도는 지수 백오프로 3회까지 합니다. 연속 실패하는 공급자는 일정 시간 폴백으로 건너뜁니다(회로 차단기).

### 품질 검사

- OHLC 범위 일관성, 결측일, 거래량 0, 분할·병합으로 보이는 급변을 검사합니다.
- 마지막 봉이 거래일 기준 3일보다 오래되면 stale로 표시합니다.
- 거래일과 휴장은 시장별 거래소 달력 라이브러리로 계산합니다.

### 생존 편향

무료 소스는 보통 현재 지수 구성만 줍니다. 현재 구성으로 과거를 검증하면, 살아남은 종목만 보게 되어 성과가 좋게 나옵니다. 구성 이력을 구할 수 있으면 날짜별로 저장하고, 없으면 검증 보고서와 화면에 이 편향을 명시합니다. 이 편향은 유니버스 평균을 끌어올리지만, 같은 날 상위 그룹과 하위 그룹을 비교하는 방식(7장)에는 영향이 작습니다.

## 5. 점수 체계 v0 (score-v0.1)

종합 점수는 다섯 팩터의 유니버스 내 백분위를 평균한 0~100 정수입니다. "같은 날 같은 시장의 다른 종목들보다 얼마나 나은가"를 뜻하므로, 하락장에서도 상대적으로 강한 종목을 가려냅니다.

### 유니버스

- 미국: S&P 500 ∪ Nasdaq-100. 한국: KOSPI 200 ∪ KOSDAQ 150. 시장마다 따로 순위를 매깁니다.
- 유니버스 밖 종목은 같은 날의 유니버스 분포에 대입해 백분위를 계산하고, '유니버스 밖' 배지를 붙입니다.

### 팩터

| 팩터 | 구성 지표 | 백분위 기준 | 비고 |
| --- | --- | --- | --- |
| 모멘텀 | 12-1개월 수익률(252거래일 전~21거래일 전), 6-1개월 수익률 | 시장 전체 | 최근 1개월은 단기 되돌림이 있어 빼는 것이 학계 표준 |
| 추세 건강도 | 종가 대비 200일선, 50일선 대비 200일선, 200일선 기울기, 52주 고점 대비 거리 | 시장 전체 | 모멘텀과 상관이 높으므로 검증에서 중복 여부 확인 |
| 품질 | ROE, 매출총이익/총자산, 영업이익률, 부채비율(역방향), 이익 변동성(역방향) | 업종 내 |  |
| 가치 | 이익수익률(E/P), FCF 수익률, 장부가/시가 | 업종 내 | 적자·자본잠식으로 음수인 지표는 제외(기존 가드 계승) |
| 성장 | 매출 성장률, EPS 성장률(전년 동기 대비) | 업종 내 |  |

변동성과 베타는 종합 점수에 넣지 않고 리스크 화면에만 보여줍니다.

### 계산 규칙

1. 각 지표는 1%·99% 지점에서 잘라(winsorize) 극단값 영향을 줄입니다.
2. 지표별 백분위를 구하고, 팩터 점수는 구성 지표 백분위의 단순 평균입니다. 구성 지표의 절반 이상이 있어야 팩터 점수를 냅니다.
3. 종합 점수는 다섯 팩터를 **동일 가중(각 20%)**으로 평균합니다. 가중치를 데이터에 맞추는 것은 7장 검증을 통과한 뒤 학습 구간에서만 합니다.
4. 다섯 중 세 개 이상 있어야 종합 점수를 냅니다. 모자라면 '산출 불가'입니다. 재무 팩터가 빠지면 '가격 기반 부분 점수' 배지를 붙입니다.
5. 업종 내 백분위는 업종 종목이 10개 미만이면 상위 업종 또는 시장 전체로 범위를 넓힙니다.

### 표시

- 등급은 백분위 구간 다섯 개입니다. 상위 10%, 상위 30%, 중간, 하위 30%, 하위 10%. 'Elite', 'Strong' 같은 말은 쓰지 않습니다.
- 팩터별 백분위와 기여도를 막대로 보여주어, 점수가 왜 그렇게 나왔는지 바로 보이게 합니다.

### 시장 국면과 합의

- 시장 국면은 종합 점수에 넣지 않습니다. 우호·중립·비우호 3단계로 따로 보여주고, 포지션 크기 배율에만 반영합니다.
- 합의는 서로 독립적인 네 렌즈만 씁니다. 가격(모멘텀+추세), 펀더멘털(품질+가치+성장), 시장 국면, 옵션(미국만)입니다.
- CAN SLIM은 점수가 아닌 참고 뷰로 남깁니다.

## 6. 진입 타이밍, 리스크, 포지션 크기

타이밍은 순위와 분리된 규칙 기반 상태이고, 기존 눌림목·모멘텀 구조를 유지하되 버그를 고칩니다. 각 상태에는 7장에서 측정한 "이 상태의 유니버스 과거 성과"가 붙습니다.

### 상태

| Setup | 상태 | 진입 가능 |
| --- | --- | --- |
| 눌림목 | 준비, 형성 중 | 예 |
| 눌림목 | 구간 밖, 구조 경고, 무효 | 아니오 |
| 모멘텀 | 돌파 확인, 초기 돌파 | 예 |
| 모멘텀 | 관찰, 과열, 돌파 실패 | 아니오 |

### 수정 사항

1. **과열은 진입 가능이 아닙니다.** 우선 방식 선택과 합의 계산에서 빼고, "눌림목을 기다리는 구간"으로 안내합니다.
2. **트리거를 명시합니다.** 모멘텀 트리거는 직전 60거래일 종가 고점입니다. 20일 고점은 '초기 돌파' 판정에만 씁니다.
3. **EMA20 단독은 지지가 아닙니다.** 이평선은 항상 가격 근처에 있어서, 혼자서는 '지지 근접도'를 부풀립니다. 스윙 저점, 거래량 노드 같은 다른 근거와 겹칠 때만 지지 Zone으로 인정합니다.
4. **목표가의 출처를 표시합니다.** 저항 Zone이 있으면 그 가격을, 없으면 ATR 배수를 쓰고 '구조 없음 · ATR 기준'이라고 적습니다.
5. **시장 국면은 실제 값을 씁니다.** 지수 가격만으로 계산하므로 과거 날짜에도 point-in-time으로 구할 수 있습니다. 기존 검증처럼 50으로 고정하지 않습니다.

### 리스크

| 항목 | 계산 | 변경점 |
| --- | --- | --- |
| 과열 | EMA20 대비 ATR 거리, RSI | 유지 |
| 변동성 | ATR% | 유지 |
| 실적 이벤트 | 발표일까지 남은 날 | 미확인이면 중간(50) + '발표일 미확인' 배지 |
| 유동성 | 20일 평균 거래대금 | 실시간 환율로 달러 환산 |
| 시장 | 시장 국면 | 3단계 상태로 |

### 포지션 크기

- 수량 = 허용 손실액 ÷ (진입가 − 손절가 + 예상 체결오차 + 주당 비용). 허용 손실액은 계좌 대비 %로 입력받습니다.
- 현금 한도와 종목당 비중 상한을 함께 적용합니다. 기존 `trade_core.position_size`를 그대로 씁니다.
- 리스크 레벨과 시장 국면에 따른 배율(1.0, 0.75, 0.5, 0.25)을 곱합니다.
- 갭 시나리오도 보여줍니다. "손절가보다 아래에서 시가가 열리면 손실이 허용액의 1.5배가 될 수 있음" 같은 문장입니다.

### 전략 보강

전략의 뼈대(품질 + 추세, 눌림목·돌파 진입, 구조 기반 손절, 리스크 기반 비중)는 유지합니다. 아래 다섯 가지를 보강합니다.

1. **청산 규칙을 추세추종의 수익 구조에 맞춥니다.** 추세추종은 "작게 자주 잃고, 가끔 크게 버는" 구조입니다. 지금처럼 목표가 1(첫 저항 또는 ATR 2.2~2.5배)에서 전량 청산하면 큰 상승의 꼬리를 스스로 자릅니다. 청산 방식을 설정값으로 만들고, 세 가지를 구현합니다.
   - A. 전량 익절: 목표가 1에서 전부 매도(기존 방식, 비교 기준선)
   - B. 분할 + 추적 손절: 목표가 1에서 절반 매도, 손절을 본절로 올리고, 나머지는 추적 손절(종가 기준 20일선 이탈 또는 최고가 대비 ATR 3배 하락)로 청산
   - C. 추적 손절만: 목표가 없이 추적 손절로만 청산
   - 최대 보유기간은 A는 20거래일, B·C는 120거래일입니다. 어느 방식을 기본값으로 할지는 7장 검증 결과로 정합니다.
2. **종목 선정과 타이밍의 시간 축을 분리합니다.** 종목 선정은 6~12개월 모멘텀(최근 1개월 제외)으로 하고, 1개월 수익률·RSI 같은 단기 지표는 진입 타이밍에만 씁니다. 단기 수익률은 되돌림이 나오는 경향이 있어서, 종목 선정 점수에 플러스로 넣지 않습니다.
3. **눌림목과 모멘텀은 점수가 아니라 기대값으로 비교합니다.** 두 점수는 서로 다른 재료로 만든 다른 척도라서, "모멘텀이 4점 높으면 모멘텀 우선" 같은 규칙은 쓰지 않습니다. 각 Setup의 현재 상태를 7장에서 측정한 과거 기대값(R)으로 환산하고, 기대값이 더 높은 쪽을 우선 방식으로 표시합니다. 검증 전에는 "비교 근거 없음"으로 둡니다.
4. **상관된 신호를 줄이고 임계값을 최소화합니다.** 추세·모멘텀·상대강도·돌파는 사실상 같은 정보입니다. Setup 점수는 꼭 필요한 요소만 남기고, 임계값(78, 62, 68 등)은 모두 설정 파일 한 곳에 모아 목록으로 보이게 합니다. 규칙이 적고 단순할수록 과적합 위험이 작습니다.
5. **포트폴리오 규칙을 추가합니다.** 종목 단위 사이징 위에 계좌 단위 한도를 둡니다. 기본값은 설정에서 바꿀 수 있습니다.
   - 동시 보유 최대 8종목
   - 같은 업종은 최대 2종목 또는 계좌의 30%
   - 열려 있는 모든 포지션이 동시에 손절될 때의 총 손실(포트폴리오 히트)을 계좌의 6% 이내로 제한하고, 현재 값을 화면에 표시
   - 새 진입 계획이 이 한도를 넘으면 사이징 계산기가 경고하고 허용 수량을 줄여서 보여줌

### 그대로 지킬 규칙

아래 규칙은 실전 경험이 담긴 부분이라 로직을 바꾸지 않고 이식합니다. 바꾸려면 검증 근거와 함께 NAMSSA에게 먼저 묻습니다.

- 눌림목 깊이는 60일 고점 대비 4~7% 조정을 가장 높게 평가하고, 1% 미만과 16% 초과는 감점
- 눌림목의 모멘텀 안정은 과매도가 아니라 RSI 52 근처를 좋게 평가
- 조정 중 거래량 감소를 좋게 평가
- 종가가 200일선 아래이거나 추세 점수가 낮으면 눌림목 무효
- 손절은 지지 Zone 하단에서 ATR 0.55배 아래(구조 기반)
- 실적 발표 임박 시 리스크 상향과 비중 축소

## 7. 검증 엔진

검증 엔진은 "점수가 높을수록 실제 성과가 좋았는가"를 유니버스 단위로 측정합니다. 앱은 이 결과를 모든 점수 옆에 근거로 보여줍니다. 이번 버전에서 가장 중요한 부분입니다.

### A. 순위 검증 (팩터와 종합 점수)

1. 기간은 가격 기준 최소 2015년부터 현재까지입니다. 재무 팩터는 PIT 데이터가 있는 기간만 씁니다.
2. 매월 말 점수로 종목을 5분위로 나누고, 다음 거래일 시가부터 21·63거래일 동일 가중 수익률을 쟽니다.
3. 지표는 다음과 같습니다.
   - 분위별 평균 수익률과 유니버스 대비 초과수익
   - 상위−하위 스프레드
   - 월별 순위 상관계수(Spearman Rank IC)의 평균, Newey-West t통계량, IC가 양수인 달의 비율
   - 상위 분위 회전율, 비용 차감 후 스프레드
4. 비용은 설정값입니다. 한국은 증권거래세를 포함하고, GPT가 현재 세율을 확인해 기본값으로 넣습니다.
5. 시장별, 기간별(2015~2019, 2020~현재), 시장 국면별로 나눠서도 봅니다.

### B. 진입 Setup 검증 (이벤트 스터디)

1. 유니버스 전 종목의 모든 날짜에 Setup 상태를 다시 계산합니다. 시장 국면은 그 날의 실제 값입니다.
2. 신호는 상태가 '준비' 또는 '돌파 확인'으로 바뀐 날입니다.
3. 체결은 기존 `execution_engine` 규칙 그대로입니다. 다음 날 시가 진입, 손절·목표·최대 보유 20일, 비용, 같은 봉에서는 손절 우선입니다.
4. 지표는 거래 수, 승률, 평균 이익과 평균 손실의 비(손익비), 기대값(R 단위와 %), Profit factor, 최대 연속 손실, 평균 보유일입니다. 헤드라인은 승률이 아니라 기대값입니다. 6장의 청산 방식 A·B·C를 같은 신호에 모두 적용해 나란히 비교하고, 포트폴리오 규칙(최대 8종목, 업종 한도)을 적용한 계좌 단위 시뮬레이션도 함께 돌립니다.
5. 기준선은 **같은 종목·같은 달의 무작위 진입일**입니다. 같은 손절·목표 규칙으로 20번 반복해, 신호의 초과 기대값과 날짜 블록 부트스트랩 95% 구간을 구합니다.

### C. 과적합 방지

- 파라미터는 미리 고정합니다. 조정은 2015~2019(학습)에서만 하고, 2020~현재(검증) 결과로 판단합니다.
- 시도한 변형의 수를 보고서에 적습니다. 여러 번 시도하면 우연히 좋은 결과가 나오기 때문입니다.

### D. 검증 엔진 자체의 검증

두 가지 합성 데이터 테스트를 통과해야 합니다.

- **무작위 보행:** 예측력이 없는 주가에서 IC 평균이 0 근처이고, 스프레드의 95% 구간이 0을 포함해야 합니다.
- **심어 둔 신호:** 점수에 일부러 예측력을 넣은 합성 데이터에서는 양의 IC를 검출해야 합니다.

### E. 결과 저장과 실행

- 실행: `goldnam validate --market us --start 2015-01-01` CLI. 로컬 또는 GitHub Actions(주 1회 + 수동)에서 돌립니다.
- 지표는 전체 시계열을 한 번에 벡터화해 계산합니다. 기존처럼 날마다 전체를 다시 계산하면 수백 종목·10년을 돌릴 수 없습니다.
- 상세 결과는 Parquet로, 요약은 Postgres에 올립니다. 요약에는 run_id, 코드·점수 버전, 데이터 기간, 유니버스, 생존 편향 고지를 담습니다.

### F. 근거 등급과 표시

| 등급 | 조건 |
| --- | --- |
| 근거 있음 | IC t통계량 2 이상, 그리고 검증 구간에서도 비용 차감 후 스프레드가 양수 |
| 근거 약함 | 방향은 맞지만 통계적으로 분명하지 않음 |
| 근거 없음 | 방향이 틀리거나 검증 구간에서 사라짐 |
| 미검증 | 아직 검증을 돌리지 않음 |

종목 화면에는 이렇게 보여줍니다. "현재 점수 구간(상위 20%)의 과거 63일 평균 초과수익 +x% (95% 구간 a~b, N=…) · 근거 있음". 근거가 약하면 약하다고 그대로 표시합니다.

## 8. Trade Lab과 체결 검증

Trade Lab의 계산은 이미 정확하므로 그대로 두고, 판단에 더 쓸모 있는 지표와 기록 기능을 더합니다.

### 유지

- Decimal 기반 비용 포함 계산, 분할매수 예산 배분, 하락 스트레스 비교, 청산 가정 비교, CSV 내보내기.
- 수수료·세금·체결오차 기본값은 사용자가 설정에서 정합니다. 통화 선택은 표시 단위일 뿐 환전이 아닙니다.

### 추가

1. **기대값 계산기.** 승률과 손익비를 넣으면 거래당 기대값(R)과 손익분기 승률을 보여줍니다. 기본값은 7장 검증에서 측정한 해당 Setup의 값으로 채웁니다.
2. **연속 손실 시뮬레이션.** 같은 입력으로 100회 거래를 1만 번 시뮬레이션해, 최대 연속 손실과 계좌 최대 낙폭의 분포를 보여줍니다. 난수 시드를 고정해 결과를 재현할 수 있게 합니다.
3. **체결 검증 헤드라인 변경.** 승률 대신 기대값과 손익비를 먼저 보여주고, 같은 종목의 무작위 진입 결과와 나란히 둡니다.
4. **거래 일지.** 실제 거래를 기록하고, 진입 당시 점수·상태·계획가를 함께 저장합니다. 나중에 "내 실제 거래가 계획대로 됐는가"를 비교하는 화면으로 이어집니다.
5. **기존 History 가져오기.** v6의 `.data/stock_analyzer_v6.sqlite`나 History JSON을 가져오되, `score_version = "v6"`으로 표시해 새 점수와 섞이지 않게 합니다.

### 브랜드 테마

색·서체·로고는 디자인 토큰 파일 하나(`web/theme/`)에만 정의하고, 컴포넌트는 토큰 이름만 씁니다. 테마는 두 개를 만듭니다.

| 테마 | 용도 | 배경 | 화면 강조색 | 로고 |
| --- | --- | --- | --- | --- |
| Personal (기본) | 개인 사용 | `#181818` (카드·패널은 이보다 한두 단계 밝은 회색) | 무채색(밝은 회색·흰색). 색은 상승·하락과 상태 표시에만 | NAMSSA가 준 참고 이미지의 블루 정사각형 + 굵은 콘덴스드 세리프 "Goldnam Sachs". 블루는 원본에서 스포이드로 추출하고, 서체는 무료 라이선스(OFL) 후보 3개 중 NAMSSA가 고름 |
| Goldnam (공개용) | 공개 배포 시 | `#181818` | Personal과 같음 | NAMSSA의 라임·블랙 로고 파일 |

브랜드 색은 로고에만 씁니다. 화면 전체는 검정 배경의 무채색으로 두어, 로고와 상승·하락 색만 눈에 띄게 합니다.

- 본문 서체는 Pretendard(한글·라틴)입니다. 숫자는 고정폭 숫자(tabular figures)로 표의 자릿수를 맞춥니다.
- 기본은 다크 모드(#181818)입니다. 라이트 모드는 설정에서 고를 수 있게 만들되 우선순위는 낮습니다. 화면의 제목과 본문은 모두 Pretendard이고, 콘덴스드 세리프는 로고에만 씁니다.
- **상승·하락 색은 설정입니다.** 한국식(상승 빨강, 하락 파랑)이 기본이고 국제식(상승 초록, 하락 빨강)을 고를 수 있습니다. 브랜드 색과 겹치지 않게 고릅니다.
- 색만으로 의미를 전달하지 않습니다. ▲▼ 기호나 텍스트를 함께 쓰고, 본문 대비는 4.5:1 이상입니다.

## 10. API

API는 `/api/v1` 아래 REST이고, 모든 응답은 같은 봉투(envelope)에 담깁니다. 웹의 TypeScript 타입은 OpenAPI 스키마에서 자동 생성합니다.

```json
{
  "data": { },
  "meta": {
    "as_of": "2026-11-21",
    "app_version": "0.0.0-a.1",
    "score_version": "score-v0.1",
    "coverage": 0.8,
    "sources": [{"name": "yfinance", "fetched_at": "...", "status": "ok"}]
  },
  "warnings": ["재무 데이터 일부 누락: 가격 기반 부분 점수"]
}
```

| 메서드 | 경로 | 용도 |
| --- | --- | --- |
| GET | `/health` | 상태, 데이터 소스별 마지막 성공 시각 |
| GET | `/search?q=` | 미국·한국 종목 검색(한글 이름, 코드, 티커) |
| GET | `/stocks/{symbol}/analysis` | 종목 분석 전체. 점수, 팩터, 타이밍, 리스크, Zone, 계획, 근거 |
| GET | `/stocks/{symbol}/prices?range=` | 차트용 일봉 |
| GET | `/universe/{market}/scores` | 스크리너. 날짜, 정렬, 필터, 페이지 |
| GET | `/market/{market}/regime` | 시장 국면과 구성 요소 |
| GET | `/validation/{market}/latest` | 최신 검증 요약 |
| POST | `/trade-lab/plan`, `/trade-lab/simulate` | Trade Lab 계산 |
| POST | `/execution-study` | 종목 단위 체결 검증 |
| GET·POST·DELETE | `/watchlist`, `/journal` | 관심종목, 거래 일지 |

- 오류는 RFC 9457(problem+json) 형식이고, 한국어 메시지와 실패한 소스 이름을 담습니다.
- 개인용이지만 API가 공개 URL에 뜨므로, 쓰기 엔드포인트는 환경변수로 정한 토큰을 요구합니다. CORS는 웹 주소만 허용합니다.

## 11. 코드 구조, 테스트, 버전

한 저장소에 엔진·API·배치·웹을 두되, 엔진은 다른 어느 것에도 의존하지 않습니다.

```text
goldnam-sachs/
  engine/goldnam_engine/
    data/         # 공급자 어댑터, 캐시, 품질 검사
    factors/      # 모멘텀, 추세, 품질, 가치, 성장 (벡터화)
    scoring/      # 백분위, 종합 점수, 커버리지
    timing/       # 눌림목·모멘텀 Setup, 지지·저항 Zone
    risk/         # 리스크 점수, 포지션 크기
    regime/       # 시장 국면
    validation/   # 순위 검증, 이벤트 스터디, 부트스트랩
    trade/        # trade_core, execution 이식본
    models.py     # 데이터 클래스
  engine/tests/
  api/            # FastAPI 앱
  jobs/           # daily_scores.py, validate.py, import_v6_history.py
  web/            # Next.js 앱, theme/
  docs/           # SPEC.md, DECISIONS.md
  render.yaml
  docker-compose.yml
  .github/workflows/ci.yml, validate.yml
  CHANGELOG.md
```

### 도구

- Python: 3.12, 패키지 관리는 uv, 린트·포맷은 ruff, 타입 검사는 mypy(엔진은 strict), 테스트는 pytest.
- 수치 함수는 속성 기반 테스트(hypothesis)를 더합니다. 예: 백분위는 항상 0~100, 결측 항목이 늘면 커버리지는 줄어듦.
- 웹: pnpm, ESLint, Vitest, 종목 분석 화면과 스크리너에 Playwright 스모크 테스트.
- 엔진 테스트 커버리지는 85% 이상입니다. 네트워크가 필요한 테스트는 `@pytest.mark.live`로 분리해 CI 기본 실행에서 뺍니다.

### CI

- PR마다: ruff, mypy, pytest, 웹 lint·테스트·빌드.
- `validate.yml`: 주 1회와 수동 실행. 검증을 돌려 요약을 Postgres에 올리고 보고서를 아티팩트로 남깁니다.
- 비밀값은 GitHub Secrets와 Render 환경변수에만 둡니다. `.env`는 커밋하지 않고 `.env.example`만 둡니다.

### 버전 규칙

- 앱 버전은 SemVer 사전 배포 표기를 따릅니다. 첫 버전은 `0.0.0-a.1`이고 화면에는 `v0.0.0-a.1`로 표시합니다. 버전 문자열은 한 곳에서만 정의합니다.
- 점수 산식 버전(`score-v0.1`)은 앱 버전과 따로 관리합니다. 산식이 바뀌면 올리고, 저장하는 모든 점수 기록에 함께 남깁니다.
- 산식이나 임계값을 바꾸면 `DECISIONS.md`에 날짜, 변경 내용, 근거(검증 run_id)를 남깁니다.

## 12. 작업 단계와 완료 기준

아홉 단계(Phase 0~8)로 나누고, 앞 단계의 완료 기준을 모두 통과해야 다음으로 넘어갑니다. 화면(Phase 6)은 검증(Phase 4)이 끝난 뒤에 만듭니다. 근거 등급을 화면에 넣어야 하기 때문입니다.

1. **Phase 0 · 뼈대와 이식**
   - 할 일: 저장소 구조(11장), 도구 설정, CI. 1장 '유지' 항목을 로직 변경 없이 엔진 패키지로 이식.
   - 완료 기준: 기존 테스트 49개가 새 위치에서 통과. ruff·mypy·CI 통과. `render.yaml`과 `docker-compose.yml` 초안.
2. **Phase 1 · 데이터 계층**
   - 할 일: 4장 전부. 어댑터, 폴백, 캐시, 품질 검사, SEC·OpenDART PIT 재무, 환율, 유니버스 구성.
   - 완료 기준: 모킹 테스트로 "실패는 성공으로 캐시되지 않음", "1순위 실패 시 폴백", "모두 실패 시 status=failed"를 검증. live 테스트로 미국 3개·한국 3개 종목의 시세와 PIT 재무 수집.
3. **Phase 2 · 팩터와 점수**
   - 할 일: 5장 전부. 벡터화된 팩터 계산, 백분위, 종합 점수, 커버리지, 일일 배치.
   - 완료 기준: 결측 처리 테스트 통과(세 팩터 미만이면 산출 불가). 미국 유니버스 하루치 계산 시간을 측정해 보고. 점수는 모두 정수이고 메타데이터를 가짐.
4. **Phase 3 · 타이밍과 리스크**
   - 할 일: 6장 전부. 1장 표의 버그 3~6번 수정, 청산 방식 A·B·C와 포트폴리오 규칙 구현, 임계값을 설정 파일로 분리.
   - 완료 기준: 버그마다 실패하던 테스트를 먼저 만들고, 수정 후 통과. 과열 상태가 우선 방식과 합의에서 빠짐.
5. **Phase 4 · 검증 엔진**
   - 할 일: 7장 전부.
   - 완료 기준: 7장 D의 합성 데이터 테스트 두 가지 통과. 미국·한국 실제 데이터 검증을 한 번씩 돌려 보고서를 제출. 보고서에는 청산 방식 A·B·C 비교와 포트폴리오 시뮬레이션을 포함. 결과가 나쁘면 나쁜 대로 보고하고, 점수를 고치기 전에 NAMSSA에게 물어봄.
6. **Phase 5 · API**
   - 할 일: 10장 전부.
   - 완료 기준: 모든 엔드포인트에 테스트가 있음. OpenAPI 스키마에서 TypeScript 타입 생성 성공.
7. **Phase 6 · 웹 화면**
   - 할 일: 9장 전부. 종목 분석 → 스크리너 → 홈 → 점수 근거 → 시장 → 기록 → 설정 순서.
   - 완료 기준: Playwright 스모크 테스트 통과. 모바일·데스크톱 스크린샷 제출. 재무 데이터가 없는 종목에서 부분 점수 배지가 보임.
8. **Phase 7 · Trade Lab과 기록**
   - 할 일: 8장 전부. v6 History 가져오기 포함.
   - 완료 기준: 기존 Trade Lab 테스트 통과. 시뮬레이션은 같은 시드에서 같은 결과.
9. **Phase 8 · Render 배포와 문서**
   - 할 일: `render.yaml` 완성, 환경변수 목록, README(로컬 실행, Render 배포, 배치·검증 실행법).
   - 완료 기준: 새 Render 계정에서 README만 보고 배포할 수 있음. 화면 하단에 버전 `v0.0.0-a.1`과 면책 문구가 보임.

- 빠진 데이터를 0이나 50으로 채우기
- 백테스트에 현재 재무 스냅샷을 쓰기

- 데이터 조회 실패를 성공처럼 캐시하기

- API 키·DB 주소를 코드나 커밋에 넣기
- 색·서체·로고를 컴포넌트에 직접 쓰기(테마 토큰만 사용)
